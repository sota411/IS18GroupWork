# 企画書: 就活の企業管理・マイページ登録を省力化するWebアプリ

作成日: 2026-09-30 / 状態: チームレビュー・提出前

## 1. 企画概要

**応募した企業はGmailから取り込み, 次の企業への登録は一度入力した個人情報を使い回す.**

就活の企業管理とマイページ登録にかかる手入力を減らすWebアプリを制作する. コア機能は, Gmailに届く登録完了・応募受付メールからの企業取り込みと, Jevを利用したマイページ登録フォームへの自動入力の二つとする. 取り込んだ企業と新しく登録した企業を同じ一覧で管理し, 締め切りやマイページへのアクセスにつなげる.

管理が苦手な利用者でも, 企業名を一社ずつ登録したり, 同じ個人情報を何度も入力したりせずに使い始められることを目指す.

## 2. 対象者と解決する課題

対象は, Gmailで企業からの連絡を受け取り, 複数企業の選考を並行して進める新卒の就活生である. 初期の動作対象はPC版Google Chromeとする.

企画の出発点は, 次の困りごとである. 需要の大きさや利用頻度は, 制作中の利用者評価で確認する.

- 選考途中の企業が増え, どこに登録したかを把握するのが大変である.
- 管理アプリを導入しても, 過去に登録した企業を入力する作業が面倒である.
- 新しい企業に登録するたびに, 氏名・住所・学校名などを繰り返し入力する必要がある.
- メールの確認を忘れ, 締め切りや次に必要な手続きを見落とす.
- 締め切りがメールや各社のマイページに分散し, 確認に時間がかかる.

「何から始めればよいか分からない」という悩みのうち, 本企画では既に登録した企業の整理と次の登録作業を扱う. 業界選びや自己分析は初期開発の対象に含めない.

## 3. コア機能

### A. Gmailから申し込んだ企業を取り込む

1. 利用者がGoogleの認可画面でメールの読み取りを許可する.
2. アプリが対象期間の登録完了・応募受付メールを検索する.
3. 企業名, マイページURL, メールから確認できる登録・応募状況を抽出し, 企業一覧に追加する.
4. 判断が曖昧なものをまとめて表示し, 利用者が必要な箇所だけ修正・除外する.

取り込み後に届いたメールも定期的に確認し, 新しい企業を追加する. 同じメールを再取得しても重複登録しない. 対象期間と最終同期時刻を表示し, 「すべての応募企業を把握できた」と誤認させない.

マイページの登録と応募の受付は別の状態として扱う. 登録完了メールだけを根拠に「応募済み」と表示しない. 広告・スカウトメールは登録の証拠にせず, 同一企業の別年度・別募集も一律に統合しない. 各記録から根拠のメールを確認できるようにする.

**期待する効果:** 管理を始めるために, 過去のメールを一通ずつ探して企業名を転記する必要が減る.

### B. 個人情報とJevを使い, マイページ登録フォームに自動入力する

1. 利用者が氏名・ふりがな・連絡先・住所・学校情報をプロフィールに一度登録する.
2. 新しい企業のマイページ登録フォームを開き, 「自動入力」を実行する.
3. Jevがフォームの項目を読み取り, 保存済みプロフィールのどの項目を入力するかを判断する.
4. ブラウザー拡張が対応する値を入力し, 入力できなかった項目を知らせる.
5. 利用者が内容を確認し, 必要な項目を補って企業サイトで登録を完了する.
6. 届いた登録完了メールを機能Aで取り込み, 同じ企業一覧に反映する.

Jevは文章を生成するモデルではなく, 与えられた状態と選択肢から構造化された判断を返すモデルである. 本企画では, フォームの各項目に対して「氏名」「電話番号」「学校名」「対応なし」などの候補を選ぶ役割を持たせる. 実際の入力値は保存した個人情報を使い, Jevに新しい個人情報を書かせない. [TypeSafe公式ドキュメント](https://docs.typesafe.ai/introduction), [Jevの紹介記事](https://typesafe.ai/blog/introducing-system-one-models-and-jev).

Jevに渡す情報は, 入力先のラベル・形式とプロフィール項目の説明を中心にする. 氏名や住所の実値を判断に使う必要がある場合は, 必要な項目だけを送る設計とし, 送信範囲を利用者に説明する. 判断が不確か, 必須情報が未登録, またはフォームが未対応の場合は, 該当項目を未入力として明示する.

最終送信, 利用規約への同意, パスワード設定, CAPTCHA, メール認証は利用者が行う. 自動入力の完了を, 企業への登録完了として扱わない.

**期待する効果:** 企業ごとに項目名や配置が違っても, 同じ個人情報を入力し直す負担を減らせる.

## 4. 差別化と導入のしやすさ

差別化の中心は, **既に登録した企業の取り込みと, これから登録する企業への入力支援を, 一つの管理手順につなげること**である. Gmail連携や自動入力の単独機能を新規性として主張しない.

| 既存サービス | 公式サイトで確認した機能 | 本企画で重視する点 |
|---|---|---|
| [コンパス就活](https://compath-life.com/students) | Gmail・Googleカレンダーとの連携, メールの仕分けと進捗管理 | 企業を取り込んだ後の, 新規マイページ登録にも同じプロフィールを利用する |
| [i-Fill](https://ifill.jp/) | マイページへの自動入力, 企業ページ・IDの管理, 締め切り通知 | 手作業で企業一覧を作る負担を, 過去と新着のメール取り込みで減らす |

比較は2026-09-30時点の公開情報に基づく. 既存サービスに同等の組み合わせがないことや, 本企画の使いやすさが優れていることは未検証である. 利用者評価では, 手入力で管理する場合に比べて準備と登録作業がどれだけ減るかを測る.

初回の操作は, Google連携, 取り込み結果の確認, プロフィール登録を基本とする. 自動入力を使うにはブラウザー拡張の追加が必要であり, 対象サイトで入力する際に実行を許可する. 利用者にAPIキーの取得, 開発環境の導入, メールの転送ルール作成を求めない.

## 5. 開発範囲と主要画面

### 初期開発で必須とする機能

- Google連携とGmailの登録完了・応募受付メールの取り込み.
- 企業一覧, マイページへのリンク, 登録と応募を区別した状態表示, 取り込み結果の修正・除外.
- プロフィールの保存・編集と, Jevによる項目判断を使った自動入力.
- 新しく届いたメールの同期と, 同期エラー・未入力項目の表示.
- メールに明記された締め切りの表示. 不明な期限は「不明」と表示し, 手動で補えるようにする.

締め切りの自動通知とGoogleカレンダー連携は, コア機能の検証後に追加を判断する. スマートフォンでの自動入力, 全採用サイトへの対応, ESや志望動機の生成, 自動応募・自動送信は初期開発の対象外とする.

| 画面・操作場所 | 利用者ができること |
|---|---|
| 初回連携画面 | Gmailの読み取り範囲を確認し, 連携と企業取り込みを開始する |
| 企業一覧・詳細画面 | 登録企業, 応募状況, 締め切り, 根拠メールを確認し, マイページを開く |
| プロフィール画面 | 共通の個人情報を登録・修正する |
| 企業サイト上の拡張操作 | 自動入力を実行し, 入力結果と要手入力項目を確認する |

## 6. 技術構成と実現条件

Webアプリを中心に, Gmail API, データ保存用のバックエンド, Jev API, Chrome拡張を組み合わせる. Chromeのcontent scriptはページのDOMを読み書きできるため, 企業サイトへの入力処理に用いる. 初期試作ではテキスト入力と標準の選択欄に対応し, 特殊な学校検索や独自の入力部品は対応状況を明示する. [Chrome公式ドキュメント](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts).

| 構成要素 | 担当する処理 |
|---|---|
| Webアプリ | Google連携, 企業一覧, 締め切り表示, プロフィール編集 |
| バックエンド | Gmailの取得・定型メール解析・差分同期, 利用者ごとのデータ管理, Jevへの問い合わせ |
| Jev | フォーム項目とプロフィール項目の対応を候補から選択する |
| Chrome拡張 | 利用者が実行したページの入力項目を取得し, 保存済みの値を入力する |

メールの読み取りにはGoogle OAuthとGmail APIを用いる方針とする. 利用者によるMCP設定を不要にするため, 初期開発ではAPI連携を優先する. 必要な権限は`gmail.readonly`とし, メールの送信・削除権限は要求しない. ただし, この権限は就活メールだけに限定された権限ではないため, アプリ側の検索・取得対象を絞る.

`gmail.readonly`は制限付きスコープであり, 一般公開時の検証や, サーバーに対象データを保存・転送する場合のセキュリティ評価が開発上の条件になる. 授業内の接続試験と一般公開の準備を分けて進める. [Google公式のスコープ説明](https://developers.google.com/workspace/gmail/api/auth/scopes).

保存する情報は, プロフィール, 企業・募集単位の記録, 締め切り, 根拠メールの識別子と必要な抽出結果を基本とする. メール全文や企業サイトのパスワードは継続保存しない. 個人情報は利用者ごとにアクセスを分離し, Google連携の解除と保存データの削除を可能にする. APIキーや認可トークンを企業ページやソースコードに埋め込まない.

## 7. 検証方法と完成の判断

以下は目標とする確認項目であり, 現時点での達成結果ではない. ダミー情報とテスト用メールで検証した後, 同意を得た利用者の環境で導入のしやすさを確認する.

| 検証対象 | シナリオと合格条件 |
|---|---|
| 企業取り込み | 登録完了・応募受付・広告・重複・曖昧なメールを含む20件以上のテスト用メールを使用する. 明確な登録・応募は正しく追加し, 広告を登録の証拠にせず, 曖昧な結果を要確認として示す |
| 再同期と状態 | 同じメールの再取得で企業が増殖しない. 新しい企業が追加され, 別年度・別募集と登録のみの状態を正しく区別する |
| 自動入力 | 項目名・配置の異なる3種類以上のテストフォームで確認する. 対応対象の値は保存したプロフィールと一致し, 不明な項目を誤入力せず, 最終送信を実行しない |
| 連携の失敗 | 認可取消・APIエラー時に同期完了と表示しない. Jevを利用できない場合は自動入力の失敗を明示し, 手入力を継続できる |
| 導入と作業量 | 初見の利用者が説明書なしでGoogle連携から企業一覧の表示まで進められるか確認する. 手入力の場合と, 初回準備時間・企業追加の手入力回数・2社目以降の登録時間を比較する |
| 情報の保護 | 他の利用者の記録にアクセスできないことと, 連携解除・データ削除後の状態を確認する |

中間発表では, 過去の登録メールの取り込み, 一度登録したプロフィールでの別企業フォームへの入力, 新着メールによる一覧への追加を一連の操作として示す. テストフォームでの成功と, 実際の企業サイトでの対応確認は区別して報告する.
